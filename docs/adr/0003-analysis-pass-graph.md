# ADR 0003. Граф проходов анализа

Статус: предложено (этап 0) · 2026-11-07 · Architect

## Контекст

Анализ должен быть: (1) графом проходов с явными зависимостями — проходы добавляют и плагины (`after=["functions"]`); (2) инкрементальным — правка пересчитывает только зависимое; (3) параллельным по функциям (rayon); (4) приоритетным — сначала то, что видит пользователь; (5) отменяемым; (6) не блокирующим UI (результаты — через снимки, ADR 0002).

## Решение

### Трейт прохода (`dasm_core::AnalysisPass`)

```rust
pub trait AnalysisPass: Send + Sync {
    fn id(&self) -> PassId;                      // "functions", "xrefs", ...
    fn dependencies(&self) -> Vec<PassId>;       // DAG; PassId = Cow<'static, str> (плагины)
    fn granularity(&self) -> Granularity;        // Program | Function
    fn invalidated_by(&self) -> &[ChangeKind];   // Definition, Function, Bytes, Type ...
    fn run(&self, ctx: &PassContext<'_>, scope: PassScope) -> Result<AnalysisDelta, Error>;
}
```

- Проход — **чистая функция** `(Snapshot, scope) → AnalysisDelta`. Он не мутирует общее состояние; дельты сливает планировщик (`AnalysisResults::apply`) и публикует новый снимок. Отсюда: параллельность без блокировок, детерминизм, простые unit-тесты на синтетической программе.
- `AnalysisDelta`: upsert/remove функций, замена **xref-группы владельца** целиком, upsert/remove строк по диапазону. Владелец — `XrefOwner::Function(entry)` или `XrefOwner::Region { pass, range }` (программные проходы), поэтому группы разных производителей не перезатирают друг друга. Индексы `xrefs_to/from` — мультимножества со счётчиком: одинаковая ссылка из двух групп не пропадает при пересчёте одной. Перезапуск прохода по одной функции заменяет ровно её xrefs — так инкрементальность не оставляет «висячих» ссылок.
- Слияние в снимок — только `SnapshotHub::update_analysis(|results| results.apply(delta))` под writer-локом (никаких «собрал результаты из старого снимка и записал» — это теряет параллельные обновления).
- `PassContext { snapshot, cancel }`: снимок не старее момента постановки задачи; `CancelToken::check()?` — в циклах.

Стандартные проходы этапа 1 (`dasm_core::pass::passes`): `entry_points` → `functions` (рекурсивный спуск + CFG, per-function) → `linear_sweep` (неразмеченный код, `Arch::is_prologue`) → `noreturn` (пропагация, tail calls) → `xrefs` (per-function) ; `strings` (program, независим).

### Планировщик (`dasm_core::AnalysisDriver`, реализация в `dasm-analysis`)

```rust
pub trait AnalysisDriver: Send + Sync {
    fn start(&self, hub: Arc<SnapshotHub>);
    fn invalidate(&self, changes: &[Change]);
    fn set_focus(&self, focus: Focus);
    fn cancel(&self);
}
```

- Один управляющий поток планировщика + пул rayon (`ThreadPoolBuilder` с `num_threads = доступные − 1`, имя `dasm-analysis-N`; не глобальный пул, чтобы не конкурировать с другими пользователями rayon).
- Очередь работ — `(pass, scope)` с приоритетом: 0 — функция под курсором, 1 — функции в `Focus::visible`, 2 — их соседи по графу вызовов, 3 — остальное в порядке адресов. `set_focus` переупорядочивает очередь, не прерывая выполняющиеся задачи.
- Задача функции может стартовать, когда для её scope выполнены все проходы-зависимости. Функции, обнаруженные в ходе анализа (call target), добавляются в очередь.
- Результаты копятся и публикуются пачкой не чаще чем раз в 100–200 мс (и сразу — для задач приоритета 0), чтобы UI не перерисовывался тысячи раз.
- `progress` в `AnalysisResults` (state, current_pass, done/total) — для строки состояния.

### Инкрементальность

`Session::apply` → `driver.invalidate(op.changes())`, если хоть один `ChangeKind::affects_analysis()` (Type, Definition, Function, Bytes). Имена, комментарии, закладки и теги **не** инвалидируют ничего — они читаются из `UserState` при отображении.

Правило инвалидации: для каждого `Change{kind, range}` — все проходы, у которых `kind ∈ invalidated_by()`, перезапускаются для функций, чьи блоки пересекают `range` (и для `Function`-изменений — для самой точки входа), затем транзитивно все проходы, зависящие от них, для тех же scope. Если изменение затронуло границы функций (появилась/исчезла функция, вызов стал noreturn), задачи для вызывающих добавляются в очередь (ограниченно: глубина 1 за итерацию, дальше — по фактическим изменениям).

| Операция | Change | Что пересчитывается |
|---|---|---|
| rename, comment, bookmark, tag | Name/Comment/Annotation | ничего (только новый снимок UserState) |
| set_type | Type | stage 1: ничего; со стадии 2 — типовые проходы/декомпилятор функции |
| define_code / define_data / undefine | Definition | entry_points (seeds из `Definition::Code`) → functions → noreturn → xrefs для затронутой функции; strings в диапазоне |
| create/delete/reset_function | Function | entry_points, functions для entry и вызывающих |
| patch_bytes | Bytes | всё, что читает байты в диапазоне: functions, xrefs, strings |

### Кто владеет функцией

Требование: результат после любой цепочки правок **совпадает с анализом с нуля**. Поэтому у каждой причины существования функции один владелец, который вычисляет её заново из исходных данных, а не накапливает.

| `FunctionSource` | Владелец | Откуда берётся | Когда исчезает |
|---|---|---|---|
| `Hint(_)` | `entry_points` | `LoadedImage::function_hints` | причина исчезает только при `DeleteFunction` |
| `User` | `entry_points` | `FunctionOverride::Create` | `ResetFunction`/`DeleteFunction` снимают причину |
| `UserCode` | `entry_points` | `Definition::Code` по адресу в исполняемом регионе | `Undefine`, переопределение как данных снимают причину |
| `CallTarget`, `TailCallTarget` | сборка мусора планировщика | ссылки из других функций | когда не осталось ссылок, или при `DeleteFunction` |
| `Prologue` | `linear_sweep` | пролог в неразмеченном коде | когда при новом проходе пролога там уже нет |

Правила:
- `Function::source` хранит **сильнейшую текущую причину**, а причин может быть несколько. Снятие причины — это не удаление: если адрес всё ещё вызывается, функция остаётся и её источник понижается до `CallTarget`/`TailCallTarget`; функция удаляется, только если причин не осталось. `DeleteFunction` запрещает функцию на адресе независимо от остальных причин, включая вызовы.
- Набор seeds в `entry_points` — чистая функция от `(function_hints, definitions, function_overrides, карта памяти)` и не зависит от уже найденных функций. Приоритет на одном адресе: `FunctionOverride::Delete` (функции нет) > `FunctionOverride::Create` (`User`) > `Hint` > `Definition::Code` (`UserCode`). `Definition::Code` вне исполняемого региона seed не даёт. Эталон — `testing::reference_analysis`.
- `entry_points` инвалидируется изменениями `Function` и `Definition`. Для своих функций (`Hint`/`User`/`UserCode`), которых нет в seeds, он применяет правило понижения выше.
- `linear_sweep` создаёт только `Prologue` и при каждом запуске снимает эту причину там, где пролога больше нет. `Prologue` — не корень сборки мусора.

Почему отдельный `UserCode`, а не `User`: `define_code` и `create_function` снимаются разными операциями (`Undefine` и `ResetFunction`), а при общем источнике владелец не может понять, какую из них отражает функция. Отвергнуто создание таких функций в `linear_sweep`: он только добавляет, поэтому `Undefine` оставлял бы функцию навсегда, а `entry_points` удалял бы чужую, и они перезапускали бы друг друга.

### Отмена

- `CancelToken` на «поколение» работ. `cancel()` (или пересоздание сессии) взводит токен; проходы проверяют его и возвращают `Error::Cancelled`, частичная дельта отбрасывается, уже опубликованные результаты остаются консистентными (`AnalysisState::Cancelled`).
- Инвалидация отменяет только задачи для затронутых scope (их токены), остальные продолжают.
- `Drop for Session` вызывает `driver.cancel()`.

## Альтернативы

- **Проходы мутируют общий `Program` под мьютексом**: проще писать, но блокировки в горячем пути и невозможность читать консистентное состояние из UI. Отвергнуто.
- **Salsa / adapton (инкрементальные вычисления «из коробки»)**: мощно, но тяжёлый фреймворк, плохо стыкуется с публикацией снимков и плагинами на Python/WASM; явный DAG + дельты проще объяснить авторам плагинов. Пересмотрим, если ручная инвалидация станет источником ошибок.
- **Async (tokio) вместо rayon**: работа CPU-bound, rayon — естественный выбор; async не нужен.

## Последствия

- Backend #2 реализует проходы как независимые типы и тестирует каждый на `testing::synthetic_program()`; планировщик тестируется с фиктивными проходами.
- Плагины этапа 3 регистрируют проходы тем же трейтом (через IDL-обёртку).
- `testing::reference_analysis` — простой однопоточный эталон для сравнения результатов планировщика на синтетике (тест-оракул).
- Детерминизм: при одинаковом входе и журнале итоговые `AnalysisResults` не зависят от числа потоков и порядка фокуса — это проверяемый инвариант (QA).

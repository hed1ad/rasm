# Модель угроз dasm

Владелец: Security · Статус: этап 1, волна B · 2026-11-07, статус мер сверен с main `e21a4d5` 2026-11-08

Связанные документы: `docs/design.md`, ADR 0001–0005, зависимости — `docs/security/dependencies.md`,
фаззинг — `fuzz/README.md`, политика раскрытия — `SECURITY.md`.

## 1. Что защищаем

| Актив | Почему важно |
|---|---|
| Рабочая станция аналитика (код, ключи, файлы, сеть) | dasm открывает вредоносные файлы; исполнение кода атакующего = компрометация машины аналитика |
| Доступность инструмента | вредонос, который «вешает» или роняет дизассемблер (OOM, бесконечный цикл, паника), — известная анти-анализ техника |
| Достоверность показанного | анализ должен показывать то, что исполнится: скрытый код, подмена байтов, ложные имена вводят аналитика в заблуждение |
| Целостность проекта | журнал — источник правды (ADR 0002); порча или невозможность открыть проект = потеря работы |
| Конфиденциальность | проект нельзя превращать в средство чтения/утечки чужих файлов (режим «ссылка») |

## 2. Границы доверия и входы

```
 недоверенное                         |  dasm (процесс пользователя)
--------------------------------------+-----------------------------------------------
 ELF-файл (вредонос)       ---------> |  Loader (dasm-elf: gimli)  -> LoadedImage
   .eh_frame, DWARF, PLT/GOT, ...     |  Arch (dasm-x86: iced-x86) decode/render
 проект *.dasm (SQLite)    ---------> |  ProjectStore (dasm-db: rusqlite) -> JSON Operation
   журнал (JSON), настройки,          |    -> Journal::replay -> UserState
   LoadOptions/Limits, путь «ссылки»  |  StoredSource::read_bytes (Linked: чтение с диска)
 аргументы CLI / config.toml --------> |  dasm-cli (clap), resolve_author
 [позже] плагины, скрипты  ---------> |  Operation API, Registry (Loader/Arch)
 [позже] IPC (мост к UI, LSP-подобные)|  сериализованные Snapshot/Operation
--------------------------------------+-----------------------------------------------
                                      |  Qt UI (dasm-qt, C++): отображает строки из бинаря
```

**Ключевое:** проектный файл — такой же недоверенный вход, как бинарь.
Проекты пересылают коллегам, прикладывают к отчётам, публикуют; `.dasm`,
полученный от третьих лиц, может быть сфабрикован целиком (SQLite + JSON).

## 3. Атакующие и сценарии

| # | Атакующий | Вход | Цель |
|---|---|---|---|
| A1 | Автор вредоноса | ELF | RCE в дизассемблере; DoS (крэш/зависание/OOM); сокрытие кода от аналитика |
| A2 | Отправитель проекта | `.dasm` | то же + чтение локальных файлов через режим «ссылка», отключение лимитов, «кирпич» проекта |
| A3 | Автор плагина/скрипта (позже) | код в процессе | плагин в процессе = полное доверие; цель модели — не дать *данным* плагина ломать ядро |
| A4 | Локальный пользователь/процесс | файловая система | TOCTOU на связанном файле, подмена файла между проверкой и чтением |

## 4. Угрозы по входам и меры

### 4.1 Недоверенный ELF / DWARF / .eh_frame (dasm-elf, dasm-x86, dasm-analysis)

| Угроза | Меры (есть / требуется) |
|---|---|
| Паника, переполнение, индексация вне границ в парсере | правило CLAUDE.md: только `Result`; clippy `unwrap_used/panic = deny`, `indexing_slicing = warn`; фаззинг `elf_load`, `eh_frame`, `dwarf`, `x86_decode` (≥ 1 ч без падений — критерий этапа 1) |
| Неограниченные аллокации (`e_shnum`, `p_memsz` = 2⁶⁴, миллионы символов/релокаций) | `Limits` (`max_sections`, `max_symbols`, `max_relocations`, `max_mapped_size`, `max_string_bytes`, `max_debug_work`) обязан проверять загрузчик **до** аллокации; `max_file_size` проверяет `Registry::load`; `MemoryMap::read` ≤ `MAX_READ_LEN`; оракул `LDR-02` в `fuzz/src/loader.rs` |
| Бесконечные циклы и рекурсия: циклы в цепочках DWARF (`DW_AT_specification`, abstract origin), CIE/FDE, рекурсивный спуск по CFG | итеративные обходы с множеством посещённых; ограничение глубины; `CancelToken` в проходах; `-timeout=10` при фаззинге |
| Пересекающиеся/пустые сегменты, «двойное» отображение адреса | `MemoryMap::new` отвергает пересечения; **пустые регионы ломают проверку — SEC-CORE-06**; `ElfLoader` пропускает `PT_LOAD` с нулевым `p_memsz` (оракул `LDR-04` в `elf_load`) |
| Сокрытие кода/данных от аналитика (overlapping insns, данные в коде, ложные символы) | листинг по адресам, явные Unknown-байты; предупреждения о пересечениях — бэклог |
| Подмена имени: управляющие символы, ANSI-escape, bidi (U+202E) в именах символов/строках | CLI экранирует управляющие символы в текстовом выводе; UI — только `Qt::PlainText`; SEC-CORE-09 |
| Уязвимости в gimli/iced-x86 | `cargo deny` (RustSec), одна версия каждого парсера (`deny.toml`), обновления по advisories |
| Демангл (C++/Rust) — отдельный парсер недоверенных строк | `cpp_demangle`, `rustc-demangle` объявлены в workspace, но пока не подключены; при подключении — fuzz-цель, лимит длины и глубины (`max_string_bytes` уже считает демангл-имена) |

### 4.2 Проектный файл (SQLite + JSON операций) — dasm-db, dasm-core

| Угроза | Меры |
|---|---|
| Вредоносная SQLite-база (повреждённые страницы, огромные BLOB, триггеры/представления) | `rusqlite` с `bundled` SQLite (версия под нашим контролем); открывать с `SQLITE_DBCONFIG_DEFENSIVE`, `trusted_schema=OFF`, не выполнять SQL из файла; проверять схему/`user_version`; лимиты `sqlite3_limit(SQLITE_LIMIT_LENGTH)` (Backend #3) |
| Неограниченный журнал/операции (OOM при открытии) | **SEC-CORE-03**: лимиты числа записей, размера JSON одной операции, длины `Batch`, общего объёма патчей |
| Глубокая вложенность JSON (`Batch` в `Batch`) → переполнение стека | лимит рекурсии `serde_json` (128) — **не отключать**; проверено тестом `deep_and_large_json_does_not_crash`; в `validate` нужен `MAX_BATCH_DEPTH` (SEC-CORE-08) |
| Линейные операции журнала и O(регионов) копия памяти на сфабрикованном журнале (подвисания UI под мьютексом сессии) | **SEC-CORE-05**: журнал на `imbl` (`6b0fbf4`), остальное открыто |
| Сфабрикованные `seq`, состояния, обратные операции | `Journal::replay` пересчитывает обратные, отвергает 0/дубликаты; **`seq` у верхней границы — SEC-CORE-04**; оракул «живое состояние == replay хранилища» (`fuzz journal_replay`) |
| `LoadOptions`/`Limits` из проекта отключают лимиты загрузчика | **есть** (SEC-CORE-02, исправлено в `6b0fbf4`): `limits` не сохраняются в проекте, из него берётся только `base`, лимиты — свойство сборки |
| Режим «ссылка»: путь из проекта указывает на `/dev/zero`, FIFO, `/proc/…`, `~/.ssh/id_rsa`, сетевую ФС | **есть** (SEC-CORE-01, исправлено в `6b0fbf4`): `open` с `O_NONBLOCK`, только обычный файл по дескриптору, лимит сборки по фактически прочитанному (`take`), сверка SHA-256 до использования. `dasm-cli` ссылку из проекта не открывает. **Требуется:** отвергать относительный путь и показывать путь пользователю до чтения в GUI (факт чтения/существования файла раскрывается, содержимое — нет) |
| SHA-256 источника не соответствует байтам | `Session::open` сверяет `source.sha256` с `program.info().sha256`, который загрузчик **обязан** считать по байтам (оракул `LDR-01`) |
| Строки из проекта в сообщениях об ошибках (`file_name`, путь) | экранирование при выводе (SEC-CORE-09) |

### 4.3 CLI (dasm-cli)

- Аргументы и `config.toml` доверенные (пользователь), но выводимые данные — нет: экранировать управляющие символы в текстовом режиме; JSON (`--json`) экранирует `serde_json`.
- `--project` по умолчанию на недоверенном проекте: коды возврата и сообщения без паник.
- `--link` пишет абсолютный канонический путь (`std::fs::canonicalize`), не относительный.
- Ссылка из чужого проекта не открывается: анализируются байты файла из аргумента `dasm analyze` после сверки SHA-256.

### 4.4 UI и FFI-мост (dasm-qt, C++) — аудит в волне C

- `unsafe` только в мосте, каждый блок с `// SAFETY:` (lint `unsafe_code = deny` в остальных крейтах — сейчас в `dasm-core` `unsafe` нет).
- Время жизни: C++ не держит ссылки в Rust-данные дольше `Arc<Snapshot>`; строки копируются в `QString`.
- Паника Rust не должна пересекать FFI (cxx превращает в abort; проверить, что недоверенный ввод не может её вызвать).
- Отображение: `Qt::PlainText` для всех строк из бинаря/проекта (иначе `<img>`/HTML в именах — rich text auto-detect), обрезка очень длинных строк при отрисовке.

### 4.5 Плагины и IPC (будущее)

- Плагины в процессе (Rust `dyn Loader/Arch/AnalysisPass`) — **доверенный код**; песочницы нет. Документировать в `SECURITY.md`; подпись/список доверенных — позже.
- Данные от плагинов — недоверенные для инвариантов ядра: `Operation::validate` на каждой операции (уже), лимиты на `Batch` и глубину (SEC-CORE-08), `AnalysisDelta` проверять (`BasicBlock` через `new`, SEC-CORE-07).
- Python-скрипты: то же, что плагины (полное доверие), но API только через `Operation`.
- IPC/сокеты (если появятся): только Unix-сокет с правами 0600 в `$XDG_RUNTIME_DIR`, без TCP по умолчанию; та же десериализация с лимитами; аутентификация по владельцу сокета.

## 5. Требования к коду (сводка для ревью)

1. Ни одной паники на недоверенном вводе: `Result`, `checked_*`, `get()`.
2. Каждая аллокация, размер которой задан входом, ограничена `Limits` или константой (`MAX_READ_LEN`, `MAX_PATCH_LEN`, …).
3. Обходы графов/цепочек — итеративные с множеством посещённых или с лимитом глубины.
4. Все лимиты — локальная политика, не из недоверенного файла.
5. Строки из недоверенных источников при выводе экранируются (терминал) или выводятся как plain text (UI).
6. Новые парсеры недоверенных данных появляются вместе с fuzz-целью в `fuzz/`.
7. Новые зависимости проходят `cargo deny check` (лицензии совместимы с Apache-2.0).

## 6. Остаточные риски (принятые на этапе 1)

- Плагины и скрипты исполняются с правами пользователя без песочницы.
- SQLite — большой C-код; доверяем bundled-версии и обновлениям по advisories.
- Сам Qt (LGPL-3.0, C++) вне Rust-гарантий безопасности памяти; на нашей стороне только plain text и короткие строки.
- Анти-анализ (обфускация, перекрывающиеся инструкции) не является уязвимостью, но снижает достоверность; учитывается в дизайне листинга.
